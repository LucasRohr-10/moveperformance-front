# MOVE Web (moveperformance-front) — Design System Reference

> Generated by design audit. Use this document to ensure new screens, components, and
> redesigns are visually consistent with the existing product.

---

## Design Library

> **This section is the single source of truth for Claude Design.**
> All new screens, components, and redesigns MUST use the library specified here.
> Do not introduce any other UI library or styling approach.

| | |
|---|---|
| **Primary component library** | **Tailwind CSS only** — no component library installed |
| **Styling method** | Tailwind CSS v4 utilities over CSS-first `@theme` tokens, plus in-house primitives in `src/components/ui/` composed with `cva` |
| **Source** | Detected in project dependencies — no `@radix-ui/*`, no `components.json`, no MUI/Chakra/Mantine/Ant Design |

### Library-specific rules for Claude Design

**Tailwind CSS only (no component library):**
- Build components with plain Tailwind classes
- Follow the spacing, color, and radius values defined in this document exactly
- **Do not introduce a component library** — the project intentionally uses vanilla Tailwind.
  `CLAUDE.md` states: *"Never upgrade the stack or add a UI/state library without a clear need."*
  Adding shadcn/ui here is a stack decision that needs the developer's approval, not a default.
- **Reuse the in-house primitives in `src/components/ui/` before writing markup.**
  See the Component Inventory below for what exists today.
- Compose conditional classes with `cn()` from `@/lib/cn` (not `@/lib/utils` — this project
  names it `cn.ts`)
- **Never hardcode a raw Tailwind palette color** (`bg-emerald-500`, `text-red-400`).
  `globals.css` says it explicitly: the semantic aliases exist *"so feature code never
  hardcodes a raw Tailwind color."* Use `success` / `warning` / `danger`.
- **Do not add `dark:` variants.** The product is dark-only; `globals.css` states
  *"there is no light theme."* A `dark:` override is always a bug here.

## Color System

### How colors are defined

Tailwind v4 CSS-first configuration. Every token lives in a single `@theme` block in
`src/app/globals.css`, which generates the utilities (`bg-card`, `text-muted`,
`border-line`, `font-display`, …). **This is the only file to edit to re-theme the app.**

The product is **dark-only**. `body` is hardcoded to `background: var(--color-bg)` and
`color: #ffffff`. There are no light-theme tokens and no `dark:` variants anywhere.

### Palette

#### Backgrounds & Surfaces
| Token | Utility | Value | Usage |
|---|---|---|---|
| Background | `bg-bg` | `#000000` | Page background (set on `body`) |
| Soft | `bg-soft` | `#0c0c0c` | Form control backgrounds, sidebar, inset surfaces |
| Card | `bg-card` | `#121212` | Card surfaces, active nav item, hover state |

#### Text
| Token | Utility | Value | Usage |
|---|---|---|---|
| Primary text | — | `#ffffff` | Body text. Set on `body`, **not** exposed as a token |
| Muted | `text-muted` | `#9a9a9a` | Secondary text, labels, table headers, placeholders |

> **Note:** white is not a `@theme` token, so component code uses the literal
> `text-white` / `bg-white` utility. `bg-white` doubles as the primary-button fill and the
> `ProgressBar` fill.

#### Borders
| Token | Utility | Value | Usage |
|---|---|---|---|
| Line | `border-line` | `#262626` | All dividers, card borders, input borders, table row rules |

#### Semantic
| Token | Utility | Value | Source | Usage |
|---|---|---|---|---|
| Success | `text-success` | `#34d399` | emerald-400 | Confirmations, active states |
| Warning | `text-warning` | `#fbbf24` | amber-400 | Warnings, blocked slots |
| Danger | `text-danger` | `#f87171` | red-400 | Errors, field validation, destructive outcomes |

Semantic tokens are used at three opacities in `StatusBadge`:
`border-<tone>/30` + `bg-<tone>/10` + `text-<tone>`.

#### Brand / Accent
There is **no accent color**. The brand expression is monochrome: black surfaces, white
text, `font-display` (Archivo Black) uppercase, wide letter-spacing. "Primary action" is
rendered as white-on-black, not as a colored button.

## Typography

### Font Families
| Role | Family | Weights loaded | Utility | Source |
|---|---|---|---|---|
| Display / headings | Archivo | 400, 600, 800, 900 | `font-display` | `next/font/google` → `--font-archivo` |
| Body / UI | Inter | 300, 400, 500, 600 | `font-sans` | `next/font/google` → `--font-inter` |
| Mono | — | — | — | Not defined — uses library defaults |

`font-sans` is applied once on `<body>`; `font-display` is opt-in per heading.

> **Weight mismatch to be aware of:** `Heading` applies `font-black` (900) and
> `font-extrabold` (800) — both loaded for Archivo. But `font-semibold` (600) and
> `font-bold` (700) appear 53 and 15 times in component code against Inter, which only
> loads 300/400/500/600. **`font-bold` (700) on Inter is not loaded** and falls back to a
> synthesized or nearest weight. Either load 700 or stop using `font-bold` on body text.

### Font Size Scale

No `fontSize` extension — the **standard Tailwind scale** applies.

Sizes actually in use, by frequency across `src/`:

| Class | Size | Count | Typical use |
|---|---|---|---|
| `text-sm` | 14px | 158 | **The workhorse.** Body text, table cells, form controls, descriptions |
| `text-xs` | 12px | 90 | Labels, table headers, metadata, error messages |
| `text-[10px]` | 10px | 36 | Button labels, badges — *arbitrary, not a scale value* |
| `text-[11px]` | 11px | 26 | `SectionLabel` — *arbitrary, not a scale value* |
| `text-2xl` | 24px | 15 | `Heading size="sm"` |
| `text-base` | 16px | 12 | |
| `text-lg` | 18px | 10 | Wordmark |
| `text-xl` | 20px | 8 | Client detail name |
| `text-3xl` | 30px | 5 | `Heading size="md"` |
| `text-4xl` | 36px | 4 | `Heading size="lg"` — **the staff page H1** |
| `text-6xl` / `text-7xl` | 60 / 72px | 4 / 1 | `Heading size="display"` (marketing only) |
| `text-[9px]`, `text-[8px]`, `text-[13px]`, `text-[17px]`, `text-[19px]` | — | 6/2/4/1/2 | *Arbitrary one-offs* |

> **8 arbitrary font sizes are in use.** `text-[10px]` and `text-[11px]` are legitimate —
> they are baked into the `Button` and `SectionLabel` primitives and the scale has no 10/11px
> step. The rest (`8px`, `9px`, `13px`, `17px`, `19px`) are one-offs, concentrated in the
> public marketing pages.

### Font Weights in use
`font-medium` (500), `font-semibold` (600), `font-bold` (700 — *not loaded for Inter*),
`font-extrabold` (800, Archivo), `font-black` (900, Archivo).

### Letter Spacing

This is the least systematic part of the design. **13 distinct tracking values are in use**,
9 of them arbitrary:

| Class | Count | Where |
|---|---|---|
| `tracking-[0.2em]` | 20 | `Button`, "Staff" chip, plans table header |
| `tracking-wide` (0.025em) | 13 | Table headers, `<legend>`, section subheadings |
| `tracking-[0.3em]` | 12 | Marketing eyebrows |
| `tracking-tight` (−0.025em) | 6 | `Heading`, wordmark |
| `tracking-[2px]`, `tracking-[0.15em]`, `tracking-[0.25em]`, `tracking-[0.12em]`, `tracking-[0.35em]`, `tracking-[3px]`, `tracking-[2.5px]` | 4/4/2/2/1/1/1 | Scattered one-offs |
| `tracking-wider`, `tracking-normal` | 1/1 | |

> `tracking-[0.35em]` (`SectionLabel`), `tracking-[0.2em]` (`Button`) and
> `tracking-[0.15em]` (the duplicate plans badge) are three different "wide uppercase label"
> treatments doing the same job. **Define a token scale for this** — it is the most visible
> inconsistency in the system.

### Text Treatments
- **Uppercase + wide tracking** is the signature label treatment: `SectionLabel`
  (`text-[11px] uppercase tracking-[0.35em]`), `Button` (`uppercase tracking-[0.2em]`),
  `StatusBadge` (`uppercase tracking-wider`), table headers (`uppercase tracking-wide`).
- **Headings are uppercase + `tracking-tight` + `font-black`** — the opposite treatment.
- The wordmark pattern is `MOVE` + `<span className="align-super text-[9px]">&reg;</span>`.

## Spacing

### Base Unit
4px — Tailwind default, 1 spacing unit = 4px. No `spacing` extension in `@theme`.

### Custom Spacing Tokens
Standard Tailwind scale — no custom extensions.

### Most Common Values Observed (staff area)
| Class | Value | Common use |
|---|---|---|
| `py-2` | 8px | **Table cell vertical padding** — by far the most repeated value (65 occurrences) |
| `px-6 py-16` | 24 / 64px | Staff page container padding — on all 9 staff routes |
| `p-7` | 28px | `Card` padding (the primitive's built-in value) |
| `p-5` | 20px | `AlertCard` padding — *diverges from `Card`'s `p-7`* |
| `mt-9` | 36px | Gap between page H1 and content |
| `mt-3` | 12px | Gap between `SectionLabel` and H1; small follow-ups |
| `mt-6` / `mt-4` | 24 / 16px | Intra-card separation |
| `gap-3` | 12px | Form row and action row gaps |
| `space-y-6` | 24px | Form field stacks, card stacks |
| `px-5 py-4` | 20 / 16px | Plans table cells — *diverges from every other table's `py-2`* |

### Layout
| Constant | Value | Notes |
|---|---|---|
| Staff content container | `mx-auto max-w-[1160px] px-6 py-16` | Repeated verbatim on all 9 staff pages |
| Staff sidebar width | `w-60` (240px) | `md:` and up; hidden below |
| Mobile header height | `h-16` (64px) | Matches sidebar header height |
| Breakpoint for the staff shell | `md` (768px) | Sidebar ↔ mobile header swap |

> Spacing uses `space-y-*` in several places (`space-y-6`, `space-y-8`, `space-y-1`) and
> `gap-*` in others. Pick one — `flex` + `gap-*` is the SpaceDev standard.

## Border Radius

### Configuration
No `borderRadius` extension in `@theme` — the **standard Tailwind v4 scale** applies.
There is no `--radius` variable; the project does not use the shadcn radius convention.

### Scale actually in use
| Class | Value | Count | Usage |
|---|---|---|---|
| `rounded` | 4px | 68 | **Effectively the only radius.** Cards, buttons, inputs, badges, selects, nav items |
| `rounded-full` | 9999px | 27 | Avatars, the `ProgressBar` track and fill, the session spinner |
| `rounded-sm` | 2px | 3 | Rare |
| `rounded-2xl` | 16px | 1 | One-off |

> The system is effectively **two radii: 4px and full.** That is a real, consistent choice —
> sharp corners matching the brand's hard-edged typography. Keep it. Do not introduce
> `rounded-lg` / `rounded-xl` in new staff screens.

## Shadows & Elevation

**Not defined — and effectively unused.** No `boxShadow` extension in `@theme`, and exactly
one `shadow-lg` in the entire `src/` tree.

Elevation is expressed through **surface color + a 1px border**, not shadow:

| Layer | Treatment |
|---|---|
| Page | `bg-bg` (`#000`) |
| Sidebar / inset | `bg-soft` (`#0c0c0c`) + `border-line` |
| Card / raised | `bg-card` (`#121212`) + `border border-line` |

Follow this convention. **Do not add shadows to new staff components.**

## Animations & Motion

### Libraries
None. No Framer Motion, no `tailwindcss-animate`. Motion is near-absent by design.

### Patterns Observed
| Pattern | Implementation | Count | Where |
|---|---|---|---|
| Color transition | `transition-colors` (Tailwind default: 150ms `cubic-bezier(.4,0,.2,1)`) | 3 | `Button`, nav links, filter chips |

No custom `duration-*` or `ease-*` values anywhere. No enter/exit transitions, no layout
animation, no reduced-motion handling (not needed at this motion level).

## Component Patterns

### Button variants observed
`src/components/ui/button.tsx`, built with `cva`.

Base: `inline-flex items-center justify-center gap-2 rounded font-semibold uppercase tracking-[0.2em] transition-colors disabled:cursor-not-allowed disabled:opacity-50`

| Variant | Classes | Role |
|---|---|---|
| `primary` *(default)* | `bg-white text-black hover:bg-neutral-200` | Main action |
| `secondary` | `border border-line text-white hover:bg-card` | Outline / secondary |
| `ghost` | `text-muted hover:text-white` | Tertiary, in-table actions |

| Size | Classes | Rendered height |
|---|---|---|
| `sm` | `px-3 py-1.5 text-[10px]` | **≈26px** |
| `md` *(default)* | `px-5 py-2.5 text-[10px]` | **≈35px** |

Plus a `fullWidth` boolean variant → `w-full`.

> **Two gaps to know about:**
> 1. **There is no `destructive` variant**, even though `--color-danger` exists. "Eliminar"
>    currently renders as `ghost` — identical to "Editar". Destructive actions have no
>    visual distinction.
> 2. **Both sizes render 10px text and sit well under the 44px touch minimum.** The
>    `followup` feature works around this with a local constant
>    `TOUCH_TARGET = "min-h-11 sm:min-h-0"` applied per button. That workaround should be a
>    size variant, not a copy-pasted string.

### Form inputs

`src/components/ui/input.tsx` — label + input + error, with `useId()` wiring and
`aria-invalid`.

Control style: `mt-2 w-full rounded border border-line bg-soft px-3.5 py-2.5 text-sm text-white placeholder:text-muted/60 focus:border-white focus:outline-none`

- Label: `text-xs font-medium text-muted`, above the control, with optional right-aligned `labelAction`
- Error: `text-xs text-danger` below, and `border-danger` on the control
- Focus: `focus:border-white` replacing the outline

> **This control string is declared in five places, in three divergent variants:**
>
> | Location | Variant |
> |---|---|
> | `components/ui/input.tsx:37` | base: `mt-2 w-full rounded border border-line bg-soft px-3.5 py-2.5 text-sm text-white placeholder:text-muted/60 focus:border-white focus:outline-none` |
> | `features/followup/form-controls.tsx:6` → `CONTROL_CLASS` | identical to base (exact duplicate) |
> | `features/plans/staff/plan-form.tsx:26` → `FIELD_CLASS` | base **+ `disabled:cursor-not-allowed disabled:opacity-50`** |
> | `features/checkins/checkin-form.tsx:42` | base **+ `disabled:opacity-50`** — a *different* disabled treatment from the one above |
> | `features/scheduling/staff/templates-panel.tsx:84,89,94,99,105` (5 inline `<select>`) | `… px-3 py-2 …` — **different padding, no focus style, no placeholder style** |
>
> Note that the two `disabled:` variants disagree with each other, so there is no single
> correct string to converge on today — the primitive has to expose disabled styling as part
> of its API or the forks will reappear.
>
> **There is no `Select` primitive.** Any new screen with a dropdown produces a sixth copy.

> **Contrast:** `placeholder:text-muted/60` resolves to ≈`#616161` over `bg-soft`, about
> **3.2:1** — below the WCAG AA 4.5:1 minimum for text. `text-muted` itself is fine
> (≈6.7:1 on `bg-card`, 7.5:1 on `bg-bg`).

### Cards / Surfaces
`src/components/ui/card.tsx` — a single div: `rounded border border-line bg-card p-7`.
No header/body/footer slots, no variants.

> `AlertCard` and the plans table deliberately bypass `Card` and re-declare
> `rounded border border-line bg-card` with `p-5` / no padding. The `p-7` default is too
> large for dense list rows, so features route around it. A `padding` variant on `Card`
> would remove those three bypasses.

### Tables
**There is no table primitive.** Six tables are hand-rolled across the staff area in
**two incompatible styles**:

| | Style A (5 tables) | Style B (1 table) |
|---|---|---|
| Used by | clients, client detail, daily slots, roster, professionals, templates | staff plans only |
| Header cell | `py-2` + `text-xs uppercase tracking-wide text-muted` | `px-5 py-3 text-[10px] font-semibold uppercase tracking-[0.2em] text-muted` |
| Body cell | `py-2` | `px-5 py-4` |
| Row rule | `border-t border-line` | `border-b border-line last:border-b-0` |
| Container | inside `<Card>` (`p-7`) | own `rounded border border-line bg-card` |
| Horizontal scroll | **none** | `overflow-x-auto` |

Style A has **no horizontal cell padding**, so the first and last columns sit flush against
the card's inner edge. Style B is the more polished one.

### Status badges
`src/components/ui/status-badge.tsx` — `label` + `tone` (`success` / `warning` / `danger` /
`neutral`), rendered as `rounded border px-2.5 py-0.5 text-[10px] font-semibold uppercase tracking-wider`.

> **A second, divergent `StatusBadge` is defined locally in
> `features/plans/staff/staff-plans-panel.tsx:25`** — same name, different padding
> (`px-2`), different tracking (`tracking-[0.15em]`), and **raw palette colors**
> (`emerald-500` / `red-500`) instead of the `success` / `danger` tokens. These are the only
> two raw-palette violations in the staff area.

### Form field composition
`features/followup/form-controls.tsx` exports `Field`, `FieldError`, `controlClass()` and
`TOUCH_TARGET` — a cleaner field-composition pattern than the `Input` primitive's built-in
label, because it works with any control, not just `<input>`. It currently lives inside one
feature. **This is the pattern to promote to `components/ui/`.**

> **A second `Field` implementation** exists at `features/plans/staff/plan-form.tsx:29`. It is
> missing the accessibility wiring the followup version has: the error paragraph gets no `id`,
> and the control gets neither `aria-describedby` nor `aria-invalid`. **Validation errors in the
> plan form are therefore not announced to assistive technology.** The followup version is the
> correct reference.

### Checkboxes and textareas
No primitives exist. `plan-form.tsx` renders two completely unstyled native
`<input type="checkbox">` — a default blue browser checkbox inside a monochrome dark UI — and
two bare `<textarea>` carrying the `FIELD_CLASS` copy. Seven such raw controls exist across
`src/`. One of the checkboxes carries a `pb-2.5` hack to line up with an adjacent `Input`,
because `Input` renders a label row and a bare checkbox does not.

## Instructions for Claude Design

> Pass this entire document to Claude Design at the start of the conversation.
> Claude Design must read the **Design Library** section first and use only that library.

### How to prompt Claude Design

```
Use the design system defined in this document. The primary component library is
Tailwind CSS only — the project has no component library and must not gain one.
Reuse the in-house primitives in src/components/ui/ listed in the Component Inventory
before writing new markup. Apply the exact color tokens, typography scale, spacing
values, border radius, and the border-not-shadow elevation convention defined below.
The product is dark-only: never emit dark: variants.
```

### Consistency rules

- **Colors**: only the `@theme` tokens — `bg-bg`, `bg-soft`, `bg-card`, `border-line`,
  `text-muted`, `text-success`, `text-warning`, `text-danger`, plus literal `text-white` /
  `bg-white`. Never a raw palette value.
- **Dark mode**: never emit `dark:` — there is no light theme.
- **Border radius**: `rounded` (4px) or `rounded-full`. Nothing else.
- **Elevation**: surface color + `border border-line`. **No shadows.**
- **Typography**: Archivo (`font-display`) for headings, Inter (`font-sans`) for everything
  else. Weights 500/600 for Inter, 800/900 for Archivo. Avoid `font-bold` (700) — not loaded
  for Inter.
- **Spacing**: stick to the observed values. Prefer `flex` + `gap-*` over `space-y-*`.
- **Equal dimensions**: use `size-*` when width equals height (`size-10`, not `w-10 h-10`) —
  already the convention in `AlertCard`.
- **Conditional classes**: `cn()` from `@/lib/cn`.
- **Touch targets**: interactive controls need `min-h-11` on mobile. Follow the
  `TOUCH_TARGET = "min-h-11 sm:min-h-0"` pattern from `features/followup`.
- **Data states**: every data-driven screen must render loading, empty, error and success.
  `CLAUDE.md` requires it. `features/followup` is the reference implementation.
- **Tables**: use Style B (the plans table) as the reference, and always wrap in
  `overflow-x-auto`.
- **Components**: check the Component Inventory first. If a primitive is missing from it,
  that is a signal to add it to `src/components/ui/` — not to inline a fourth copy.
